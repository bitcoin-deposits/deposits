# bitcoin deposits
## 概要

理想的なピアツーピア型の電子キャッシュは、オンライン決済を一方の当事者から他方へ迅速かつ最小限の準備で直接送金できるものである。lightning ネットワークはその解決策の一部を提供するが、信頼できる第三者が自分に代わって状態を管理する必要がある場合、本質的な利点は失われる。我々は、検証可能な台帳と担保のウェブを用いてこの問題の解決策を提案する。オペレーターは台帳の更新をピアにブロードキャストし、監査可能なアカウントの記録を作成する。ウォレットは不正の証拠をそれらのピアにブロードキャストし、ピアは台帳が誠実なオペレーターを維持することを保証する。一方的な退出は、ネットワークが存続する限り資金が利用可能であるという保証に置き換えられる。流動性の維持を委任し、セットアップ手数料を回避し、オフラインでの支払い受取が可能であり、ベースレイヤーから独立してスケールするネットワークに到達する

## はじめに

bitcoin deposits は、高速でスケーラブルな鍵管理された資金を、トラストレスに、オフチェーンで提供することを目指す。オンチェーンの活動は台帳の数とリザーブのローテーション頻度に応じてスケールする。スループットはネットワーク内の台帳数に対してほぼ線形を若干上回る形でスケールし、数兆のウォレットにわたる毎秒数百万トランザクションが実現可能である

明確なトレードオフがある：
- 一方的な退出がない：オペレーターが失敗した場合、資金はネットワーク内に留まる
- プライバシーがない：検証には透明性が必要である
- 断続的な可用性：デポジットの可用性はオペレーターの可用性に依存する。ウォレットは可用性を高めるために資金を分散させるべきである

我々は、ウォレットの体験が高速なベースレイヤーに類似し、lightning ネットワークに近い決済経済性を持つと期待している

## 台帳

台帳は、前回の更新の hash を含み、台帳のオペレーターによって署名された、不変の更新チェーンである。更新の種類によって、いつどのように使用できるかを規定するルールが異なる。台帳は自己記述的であり、その更新は公開され否認不可能であるため、誰でも適合性を評価できる

台帳には単一のアクティブなオペレーターがいるが、メッシュによって協調的に維持される。どのオペレーターでも台帳を作成できるが、消失または不正になった場合、別のオペレーターがリザーブとともに割り当てられる。現在アクティブなオペレーターは、最新の共同署名された更新に署名するために使用された公開鍵によって識別される

## デポジット

デポジットは、miniscript によって管理される、送受金が可能な安定したアカウントである。開設時に手数料スケジュールが設定され、資金の受取にウォレット署名のリクエストが必要かどうかも設定される。オペレーターは同一台帳上のデポジット間の送金およびオンチェーンでの退出を許可しなければならない。デポジットが lightning インボイスを支払えるようにすべきである

オペレーターの裁量により、デポジットに代わってオンチェーンのファンディングオファーや lightning インボイスを作成できる。その場合、これらはクォーラムメンバーによって共同署名されるべきであり、ウォレットはこの署名を検証すべきである。オファーとインボイスは台帳の一部ではないため、署名の検証と証拠としての保持はウォレットの責任である

## 手数料

デポジット間、オンチェーン、lightning を通じた送金には、台帳のオペレーターに支払われる手数料がある。また、指定された期間で残高に定期的に適用される手数料もある。すべて新しいデポジットの開設時に交渉される。手数料は指定されたブロック数の後に変更可能であり、指定されたブロック数の事前通知と、開設時に交渉された調整ごとの割合制限の範囲内で行われる。クォーラムは、最終的に自分たちが責任を負う可能性のある不採算な状況を生み出す更新への共同署名を拒否できる

## 送金

送金の基本形態は、同一台帳上の2つのデポジット間の2段階操作である：デポジットが送金リクエストを発行する。十分な資金がある場合、支払条件付きの資金ロックが台帳に追加される。タイムアウト前に支払条件が満たされた場合、オペレーターの手数料を差し引いた資金が送金者から受取者に移動する。タイムアウトに達した場合、より少額のオペレーター手数料を差し引いてロックが解除される。miniscript の支払条件により、同一台帳上の他のデポジットにブリッジおよび流動性サービスを提供するのに十分である

## lightning

lightning チャネルを持つオペレーターは、デポジットが lightning ネットワークを通じて送受信することを許可できる。デポジットが lightning インボイスをリクエストすると、オペレーターは自身の lightning ノードを通じてインボイスを作成し、クォーラムメンバーに共同署名を求めて支払い時にデポジットへの入金を約束していることを証明する。ウォレットはこの共同署名されたインボイスを証拠として保持すべきである。デポジットが lightning インボイスの支払いをリクエストすると、オペレーターは自身の lightning ノードを使って支払い、preimage を取得した後にデポジットから引き落とす

支払者と受取者が同じオペレーター上のデポジットである場合、オペレーターは lightning を経由せずに内部で決済し、それぞれのデポジットに直接入金・引落しを行うことができる。これによりルーティング手数料と障害モードを回避しつつ、同じ会計上の保証を維持する

## クーリエ

送金リクエストは同一台帳上のデポジット間でのみ資金を移動する。台帳間で資金を移動するために、ウォレットはクーリエを使用する — クーリエとは複数の台帳にデポジットを保持し、それらの間で送金を運ぶサービスである。クーリエはリレー上でキャパシティと台帳ごとの方向別手数料を公開する。ウォレットが台帳Aから台帳Bに送金したい場合、クーリエのデポジットへの送金ロックを作成し、クーリエに宛先台帳上の自分のデポジットから受取者への送金ロックの作成をリクエストする。両方のロックが確立されると、ウォレットは受取者に preimage を開示し、受取者はクーリエからの送金を完了する。開示されると、クーリエはこの同じ preimage を使って送金者からクーリエへの送金を完了する

これは標準的な hash タイムロック契約パターンである。クーリエの送信側タイムアウトは受信側より厳密に早いことが期待され、ウォレットが開示しない場合、両方のロックが期限切れとなりどちらの当事者も資金を失わない。タイムアウト保証はオペレーターによって強制されるため、それ以上の信頼は不要である

クーリエは台帳ごとの手数料を設定すべきである：サービスする各台帳に対して fee_in と fee_out を設定する。ウォレットはルートコストを送信元の fee_out と宛先の fee_in の合計として見積もる。クーリエは利用可能な流動性に基づいて台帳ごとに手数料を変動させ、自然にポジションを再バランスできる。ウォレットはリレー上の広告を通じてクーリエを発見し、手数料、キャパシティ、またはカバレッジに基づいて選択する

## 通信

ウォレットとオペレーター間、およびオペレーター間のすべての通信は nostr リレーを使用する。台帳の更新はリレーが保持する永続的なイベントとして公開され、恒久的な監査可能記録を作成する。ウォレットとオペレーター間のリクエストとレスポンスは、短いリレー TTL を持つエフェメラルイベントである。オペレーターは自分の条件を置換可能なイベントとして公開し、ウォレットが中央集権的なディレクトリなしにオペレーターを発見・比較できるようにする

このアーキテクチャにより、ウォレットは永続的な接続を必要としない — 無期限にオフラインにでき、それらを保持する任意のリレーからイベントを再生して追いつくことができる。オペレーターは彼らが監視する任意のリレーを通じて到達でき、リレーの選択はデプロイメントの決定であり、プロトコルの制約ではない

## リザーブと担保

リザーブは、台帳の債務の合計以上の金額を持つ utxo に保持され、クォーラムの過半数によって支出可能であり、相当な期間後にオペレーターへのフォールバックがある

担保はオペレーター自身の資本であり、クォーラムメンバーの台帳に預け入れられ、ロックされる。各メンバーは、オペレーターが資金を提供し指定された期間ロックする担保デポジットを保持する。台帳の総債務は、いずれかのメンバーが保持する最小の担保ロックの2倍に制限され、クォーラムの期間は最短のロック時間に制限される。これにより、担保のウェブはカストディ移転をカバーするのに常に十分な裏付けを持つことが保証される。資本効率を改善するために同じ担保デポジットが複数の台帳を裏付けることができるが、ウォレットは担保ソースが重複しないオペレーターを優先すべきである

債務は新しいファンディングオファーやインボイスの作成時に強制される。オペレーターはリザーブを超えるか、最小担保ロックの2倍を超えるか、いずれか低い方を超えて台帳の総債務を押し上げるオファーやインボイスを作成できない

## クォーラム

オペレーターは、メンバーの台帳に担保を預け入れてロックすることで、他のオペレーターにクォーラムへの参加を依頼する。リクエストには担保のコミットメント（金額とロック期間）とメンバーの条件（台帳上のデポジットが満たすべき最低手数料スケジュール）が含まれる。各メンバーは自身の台帳を運用しなければならず、オペレーターが非適合であることが証明された場合、オペレーターの担保を没収できる。メンバーはクォーラムメンバーシップ期間中の手数料スケジュールの制限を指定する — オペレーターは最も厳格なメンバーの最低額を下回る手数料でデポジットを開設できず、カストディ移転後に不採算な債務を引き継ぐことからメンバーを保護する

クォーラムが確立されると、リザーブは新しい multisig utxo にローテーションされる。メンバーは有効な更新に共同署名し、オペレーターが非適合な更新に署名した場合のリカバリに参加する。より大きなクォーラムは通信オーバーヘッドを増加させるが、オペレーターリスクを低減し、可用性を高め、共謀をより困難かつ高コストにする。ウォレットはより大きなクォーラムを優先すべきである

## 経済的抑止力

このプロトコルは一方的な退出を経済的抑止力に置き換える。クォーラムメンバーは不正に対して行動する直接的なインセンティブを持つ。通常の運用中は担保に対する控えめな手数料を得るが、証明可能な非適合行動が発生した場合、自分の台帳上のオペレーターの担保全額を没収する立場にある

ウォレットが検閲を疑った場合、認証付き配信を通じてクォーラムメンバーにリクエストをエスカレートできる。メンバーは少額の手数料でリクエストの hash を自身の台帳に埋め込み、因果的にアンカーされた証拠を作成する。オペレーターがリクエストを処理しない場合、メンバーは証拠と紛争を開始する経済的インセンティブの両方を持つ

lightning インボイス詐欺も同じ抑止パターンに従う。オペレーターは preimage を受信したかどうかを知っているが、ウォレットは知らない。しかし、いかなる支払者もウォレットに preimage を提供する可能性がある。単一の確認された窃盗が紛争、リザーブの差押え、担保の没収を引き起こす。単一の支払いを盗む報酬は限定的だが、リスクは存在的であり、第三者の協力なしには形式的に証明不可能であるにもかかわらず、lightning の窃盗を経済的に非合理的なものにする

検閲と lightning 抑止の両方の障害モードは、クォーラムの全会一致の共謀である。プロトコルは協力して窃盗するクォーラムに対しては保護できないが、担保のウェブは共謀のコストが利益を上回ることを保証する。ネットワークの透明性により、ウォレットとディスカバリーマーケットは資金を預ける前に疑わしいクォーラム構造を特定できる

## 時間

絶対時間はベースレイヤーに対して測定される。チェーン再編成時の安定性を維持するために、許容範囲は合理的な確認数を超えてはならない

より高い許容範囲が必要な場合、因果的順序に依存する。暗号台帳は merkle チェーンである。各更新はそれ以前のすべての更新の後に作成されたことを証明するが、チェーン外の情報については何の保証も提供しない。分散的な順序付けを構築するために、共同署名に共同署名者の台帳からの最新の更新 hash を含めることを要求する。その hash は現在の更新の hash に組み込まれ、チェーンの一部となるとともに、台帳オペレーターが共同署名するすべての他のチェーンの一部にもなり、因果性のウェブを作成する。これは時間を明示的に証明することはできないが、特定の情報が特定の順序で作成されたことを証明できる

## 不正証明

情報が誤った順序で作成されたことを暴露することで、様々な種類の不正を証明できる。通常のネットワーク操作で情報が含まれない場合、証拠の hash を含むアクティビティを作成することで密輸できる。オペレーターが署名した更新に組み込まれると、証拠は順序付けにおいて非適合な場所で作成されたことが明らかになる：

- オペレーターが、オンチェーンで特定のアドレスに送金された資金をデポジットに入金するオファーをしたにもかかわらず、適切な入金を含まないが、入金前に許可された確認数を超えるブロック hash を含むチェーンを明らかにする台帳更新に署名した場合

- オペレーターが、デポジットに代わって lightning インボイスを作成したにもかかわらず、preimage がチェーンで明らかにされているにもかかわらずデポジットに入金していない台帳更新に署名した場合

- 現在の台帳 hash を、自身のチェーン内の後の hash に先行するものと宣言する共同署名

- 争議中の台帳のクォーラムのメンバーが、アクティブであったにもかかわらず、指定されたブロック数以内に不正の証明に従って行動しなかった場合

- 非適合な台帳更新への署名または共同署名

不正証明は、証拠と埋め込まれた hash を被告オペレーターの台帳に接続する因果チェーンで構成される。チェーンは共同署名された更新のシーケンスであり、各更新は前のリンクの台帳からの member_ledger_hash を含む。検証者は検索することなくチェーンをたどり、各リンクが署名された更新であること、および証明 hash が埋め込まれたデータと一致することを確認する

## リカバリ

台帳が利用不能または非適合になると、クォーラムメンバーは最後の適合更新から台帳の独自の継続を作成できる。新しいクォーラムを確立し、担保の証明を提供しなければならない。メンバーはその後、前のリザーブ出力を潜在的な次のチェーンの抽選に支出するよう調整しなければならない。この抽選の勝者は自身のチェーンに取得更新を追加し、他は譲渡を追加する。ウォレットは同じ台帳にアドレスし続け、クォーラムによって共同署名された応答のみを受け入れる。定期的に、および期待される共同署名を持つ応答がない場合、ウォレットはネットワークに照会し、台帳の更新を再生してカストディの変更を特定すべきである

非適合が偶発的と思われる場合（例：台帳が一定のブロック数の間利用不能になった場合）、カストディの変更は敬意を持って行われなければならない：台帳の債務をカバーするために必要なリザーブの金額のみが抽選に送られ、おつりはオペレーターの公開鍵に送り返される。担保の管理は影響を受けない

非適合の証明が存在する場合、必要なリザーブを超える金額はクォーラムのメンバー間で均等に分割され、メンバーの台帳に保持された担保は没収が許可される

## ネットワークの健全性

一つの直接的な攻撃は、共謀するオペレーターの島を形成することである。台帳全体で相当な債務を構築した後、協調して退出し、失われた担保を超える資金を盗む。ネットワークはこれに対して防御できるが、内部価値が非共謀ネットワークとの接続担保を超える領域では例外である。より高い担保比率とより大きく多様なクォーラムはこれらのポケットが形成される可能性を低減するが、意図的に形成される可能性があり、すべてのウォレットにネットワーク全体を評価することを期待できない。代わりにディスカバリーマーケットは、賞金収集アルゴリズムなどのグラフ分析に基づくオペレーターの説明責任の指標を公開すべきである

## 結論

我々は、窃盗には共謀を必要とするが、共謀は盗まれる価値の増加よりも速くリスクにさらされる担保を増加させる担保ネットワークを提案する。我々はこのネットワークを使用して、完全なリザーブに裏付けられた暗号台帳を保護する。これらの台帳は、事前に交渉された手数料と引き換えに、オフラインウォレットに代わってアカウントをサービスする。台帳プリミティブは、基本的なスマートコントラクトに十分な miniscript 支払条件をサポートする。ネットワークはほぼ線形にスケールし、大規模なネットワークが数十億のウォレットと従来の決済ネットワークを超えるトランザクションボリュームを提供することを可能にする
